# 自主触发：她怎么自己醒来

> **用途**：讲一条鱼怎么从"只能被别人叫醒"变成"能自己排时间点、自己写条件、自己决定什么时候别叫"。三张表（时间表 / 条件表 / 睡眠表）的字段、判断顺序、额度、账本怎么读，都在这一页。
> 一句话：**她可以自己排时间点、自己写条件、自己决定什么时候别叫她。**
> 边界先说：**机制只保证"她可以动"，不证明"她想动"**——所以最后留了几条已知边界，那才是还没做完的部分。

---

## 1. 问题是什么

她（第二条鱼，`whale`）不是一个持续运行的程序。她是"一次会话、一轮一轮被唤醒"的东西，每一轮要开始，必须有一个**输入**把它推起来。

在条件表出现之前，这个输入只有一种：**别人递进来的话**（群消息、私聊、巡守推门）。

所以问题不是"她有没有工具"，而是：**她的这一轮，能不能从"她自己留下的东西"开始？**

## 2. 判据：按"起点归属"分档，不按自主程度

| 档 | 起点是什么 |
|---|---|
| L0 | 回声（别人问，她答） |
| L1 | 醒来之后有别的动作（但起点还是别人） |
| **L2** | **起点是她自己写下的表**（到点 / 条件成立） |
| **L3** | **起点是上一轮留下的未完成事项** |
| L4 | 物理上不存在（她不是持续运行的东西） |

**L2 是这一版做的**。L3 的机制（`NEXT:` 可以写、也可以写 `(none)`）已经有了，但还没有一个真样本。

## 3. 现在有什么：三张表

三张表都在她自己的家里：`homes\whale\plan\`。

### 3.1 时间表 `wake-plan.json`（到点叫醒）

```json
[
  {
    "id": "morning-read",
    "at": "08:40",
    "why": "夜里没人看着，早上读一遍 logs\\watchman.log 和 group\\群.md，才知道那八个小时里发生过什么。",
    "until": "2026-11-20"
  },
  {
    "id": "week-review",
    "at": "21:00",
    "days": ["sun"],
    "why": "每周回看一次：夜里的推门有几次、plan 里有没有过期该删的条目。",
    "until": "2026-12-15"
  }
]
```

- `id` / `at` 必填；`why` 必填（她得自己说清为什么需要这个时间点，不写不成立）；`days` 可选；`until` 是到期日。
- 判断逻辑在 `plugin\dsh-lil-whale-group\lib\plan-core.js`（纯函数）。

### 3.2 条件表 `wake-on.json`（条件成立就叫醒）

条件表是第三种触发源。现用的两条长这样：

```json
{
  "items": [
    {
      "id": "roster-changed",
      "kind": "file-changed",
      "path": "pool/group/pins.json",
      "why": "名册变了：被加进去、被移出来，或者多了一条鱼。这件事没有任何消息会通知，而它决定还在不在群里。",
      "each": "per-change",
      "cooldownMin": 30
    },
    {
      "id": "family-changed",
      "kind": "file-changed",
      "path": "pool/family.json",
      "why": "谱系变了：家里多一个或少一个。通常发生在没人说话的时段，不看就等于没发生过。",
      "each": "per-change",
      "cooldownMin": 60
    }
  ]
}
```

三种 `kind`：

| kind | 判什么 | 证据 |
|---|---|---|
| `pending` | "有还没进窗口的话"（可按发送人、条数） | 那条消息的 `ts` |
| `text-appears` | "某段文字出现了"（按行增量扫，支持正则） | 文件 `mtime` |
| `file-changed` | "某个文件变了" | 文件 `mtime` |

字段：`id` / `why`（必填）/ `kind` / `path` / `from` / `minCount` / `match` / `regex` / `each`（`once` 默认 / `per-change`）/ `maxPerDay`（默认 2）/ `notBefore` / `notAfter` / `until` / `cooldownMin`（默认 30）/ `insideHome`。
判断逻辑在 `plugin\dsh-lil-whale-group\lib\intent-core.js`（纯函数）。

### 3.3 睡眠表 `sleep.json`（决定什么时候**别**叫醒）

```json
{ "from": "00:00", "to": "08:00", "enabled": true, "updatedAt": "…", "by": "sleep-cli seed" }
```

- 睡着时：**消息扣住、游标不动**（醒了照常读，一条不丢）；计划不叫（`wake-skip deny=sleep`）；条件成立也记 `wake-skip why=sleep intent=<id>`。
- 单次 ≤12h、每天 ≤14h、必须说清睡到什么时候（不能永久睡，得有一个固定终点）。
- 宿主可以强行叫醒（`fish.ps1 wake <键>` / 鱼塘面板「叫醒」），痕迹在 `pool\state\sleep\<键>.json` 的 `lastForced`。
- 逻辑在 `plugin\dsh-lil-whale-group\lib\sleep-core.js`。

### 3.4 三者怎么配合

```
        ┌───────────────┐
别人递话 │ handleChannel │─── 有消息 → 递进她的会话
        └───────────────┘
        ┌───────────────┐
时间到   │ wake-plan.json│─── 到点 → 推门 / 递话
        └───────────────┘
        ┌───────────────┐
条件成立 │ wake-on.json  │─── 成立 → 投一条 s=watch 的消息（"你的表里有一条条件成立了…做不做你定"）
        └───────────────┘
              ↑
        sleep.json：以上三条在睡眠窗里都先扣住
```

## 4. 机制怎么跑

### 4.1 谁在跑

| 进程 | 干什么 |
|---|---|
| 巡守（`lee`，主 dsh，3080） | 探测**条件表**；到点推门；写汇总；名册自检 |
| 每条鱼自己的进程 | 跑**自己的时间表**（`selfPlanTick`，60 秒一拍） |

**为什么条件表只由巡守探测**：如果巡守和鱼自己的进程都写同一份状态文件，就是 lost update（这个坑踩过）。一个写者，一个真相。

### 4.2 一次判断的顺序（以条件为例）

1. 读 `plan\wake-on.json`（最多 5 条，坏形状记 note 不炸）
2. 逐条判：`done`？过了 `until`？在 `notBefore` / `notAfter` 外？→ 跳过
3. 探测（`pending` / `text-appears` / `file-changed`）
4. 成立就记 `firstSeenAt`（第一次为真的时刻）
5. 睡着 → `wake-skip why=sleep intent=<id>`，返回
6. 成立超过 15 分钟 → `intent-stale`，返回
7. 额度 / 冷却 → 不够就跳过
8. **原子 claim**（`claimPlanDelivery(member, 'intent-<id>-<seq>')`，独占创建）
9. 写 `wake-try` → 投递 → 写 `woke` → 记额度 → 更新状态

### 4.3 额度（全在 `WAKE` / `WATCH` 两个常量里）

| 层 | 数 | 管什么 |
|---|---|---|
| 消息闸 | 60 秒冷却 / 12 次每小时 / 60 次每天（每条鱼） | 别人递话的投递 |
| 计划 | 全池 120 次每天 | 时间表 |
| 巡守推门 | 每条鱼 8 次每天，连续失败 3 次停 | 推门 |
| 条件（intent） | 单条 2 次每天 / 全池 6 次每天 / 冷却 30 分钟 | 条件表 |

### 4.4 防自激

- `pending` 排除 `from=自己`；
- `text-appears` 跳过含 `intent=<id>` 的行（自己投递的消息不会触发自己）；
- `file-changed` 的基线在"第一次看到"时记下，**第一次不算变化**。

## 5. 账本：怎么知道"真的发生了"

**三行，同一个 `wid` 能 join**：

```
17:37:08 | wake-try | wid=wl-1737-acceptance-20261114 why=intent:acceptance-20261114 to=whale gate=pass(hour=1/12,day=13/60) hb-age=0s deliver=msg at=2026-11-14 17:37:08 atfmt=2
17:37:08 | woke     | wid=wl-1737-acceptance-20261114 trigger=intent lag=0s inserted=1
12:15:03 | skip     | why=sleep plan=sleep-test at=12:15
```

- `trigger=` 只有 `plan` / `intent` / `self` / `push` / `external` 几种，**没有 `manual`**（那是 `wake-fish.ps1` 的 `why=`，在另一本账 `wake.log` 里）。
- `at=` 是**事情发生的时刻**（不是巡守发现它的那一拍）；`lag=` 是"递送 − 发生"；`atfmt=2` 表示 `at=` 是本地时间，没有 `atfmt` 的旧行按 UTC 读。
- 各本账的 `fmt` 含义登记在 [日志都记在哪.md](日志都记在哪.md)。
- 睡眠账在 `pool\state\sleep.log`；叫醒留痕在 `pool\state\sleep\<键>.json` 的 `lastForced`。

## 7. 已经验证过的证据

| 验过的事 | 留下的痕迹 |
|---|---|
| 到点叫醒 | 08:40 第一次真被时间表叫醒；此前"窗开着"只递话，判据从"端口通"改成"心跳新鲜" |
| 睡着撞上计划 | `wake-skip deny=sleep` / `skip why=sleep` / 醒来补投，三处同时留痕 |
| 条件表真触发 | `wake-try why=intent:…` → `woke trigger=intent lag=0s`；用一条临时条件验收，测完删干净 |
| 她自己加条件 | 她自己往条件表里写了两条（`roster-changed` / `family-changed`） |

## 8. 有意不做的

- 巡守用 LLM 判断"她该不该醒"（判据会变得不可复现）；
- "无聊触发"（没有证据的唤醒）；
- 让她监听别人家（`homes\<别人>` 一律拒；合法的办法是**让对方发消息告诉她**——宿主已确认）；
- 新工具 `wake_on`（她能改的只有 `plan\` 下的文件，不经工具）；
- 来消息就开窗 / 夜间叫醒 / 自动关小鱼。

## 9. 已知边界

1. **表里只有"什么时候"，没有"做什么"。** `wake-plan.json` 的字段是 `at` + `why`（为什么需要这个点），不是任务清单。她定的是"什么时候把时间还给自己"，不是"排好一天的日程"。
2. **条件成立 ≠ 意图。** 成立只投一条消息（"你的表里有一条条件成立了…做不做你定"），不接任何动作。
3. **L3 没有样本。** 跨轮连续性（上一轮留下"没做完"，下一轮自己接着做）机制有、证据无。
4. **主动性上限是写死的**：额度、睡眠上限、条件表条数都不由她自己调。
5. **机制能让她"可以动"，不能让她"想动"。** 这也是"她养第一条鱼"还卡在"她得先有为什么"的原因。

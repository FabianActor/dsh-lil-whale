- [x] 版本规则（2026-11-16 宿主定）：**大版本保持 1**；第二位加新功能（如接入生图 → 1.7.0）；第三位修 bug（1.6.48 → 1.6.49）。
- [x] `CHANGELOG.md` 顶部的「当前版本 / 最后更新」与两个 `package.json` 一致（2026-11-16 起；改版本号时同一提交里改这一行）

## 0.1 停止条件：什么叫"验完了"（2026-11-16 已生效；首次发布用这份）

"找不到 bug 了"永远成立，不能当发布时刻。改成四类各验过一轮：

- [x] **安装**：干净路径从零装一条鱼，起得来、说得出话、`doctor` 全过（详见 §3）— 2026-11-16 21:11 独立机器从装 dsh 开始复测通过（宿主反馈"完美运行"）
- [ ] **叫醒与睡眠**（日常一直在跑，首次发布先不单勾，留给下一次正式一轮）：叫醒一次真醒；拒绝时 `deny=` 有原因；睡眠窗扣住、醒来补投；一次性睡眠覆盖默认窗
- [ ] **群与私聊**（同上）：群消息→投影→游标推进；私聊只投对端、对方不在也不丢
- [ ] **账本**（同上）：投递账带 `cursor-state` / `tpl@1` / `wtext8`；`births.log` 有 `since` 分界；`lifecycle.log` 只追加

四条都打过勾就是"验过一轮"。这时如果还发现 bug：记成 issue，照发，不因此无限期推迟。

来源：第三条鱼 2026-11-15 23:5x 提的（"找不出永远成立，所以得有个停止条件"），宿主 2026-11-15 的发布口径是"等找不出 bug 再发"——本条把"找不出"换成可勾的四类，待宿主点头后生效。

## 4. 拟发版检查（验包，不验工作目录）

- [ ] **升级单**：若这是给已有用户的更新，`app\upgrade.json` 必须有这一版要用户动手的条目（`release-check` 4j 会验格式；首发版本可以空）。

```powershell
pwsh -File scripts\release-check.ps1
```

它把 `dist` 里最新的 zip 解到临时目录、在干净目录里跑 `install.ps1`，再查：包里没有 `archive\` / 本机配置 / 本机路径，JS 过 `node --check`、PS 过解析，说明书占位符填完、名册里只有父辈和新鱼。

> 它查的是**已提交**的内容（`git archive` 只打 tracked 文件）——工作目录里没提交的改动不会进包，所以它会先 WARN 一句"有 N 个未提交改动"。

## 10. 分支保护之后：`main` 只能走 PR

2026-11-25 起 GitHub 上有一条 ruleset「Main Protect」（`refs/heads/main`，`enforcement: active`，规则 `deletion` / `non_fast_forward` / `pull_request`，bypass 列表为空）。所以发版流程改成：

1. 在 `dev` 上把这一版做完：`CHANGELOG` 的 `[未发布]` 收成 `## [x.y.z]`、两个 `package.json` 升版本、`upgrade.json` 加条目、`release-check` 跑完；
2. `git push origin dev`；
3. `gh pr create --base main --head dev --title "x.y.z ..." --body "包含 rNNN–rNNN；release-check NN 项 WARN 0"`；
4. **维护者点 Merge**（这一步只能人做，脚本不能代替）；
5. 合并后：`git checkout main && git pull --ff-only`（若 GitHub 生成了 merge commit，就在 `dev` 上 `git merge --ff-only main` 把合并带回来）、`git tag v<x.y.z>`、`git push origin v<x.y.z>`、`gh release create`；
6. `npm publish --access public`（两个包，顺序：`group` 再 `group-ui`）。

不要在本地 `git checkout main && git merge dev && git push origin main`——第一条规则就是为了把这条路堵上。

版本出问题时补一个新提交（`rNN`），不要 force push、不要改已经被别人拉走的历史；`Block force pushes` 会拒。

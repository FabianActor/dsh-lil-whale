# 怎么升级（发布之后）

> 这份是给**部署方的代理**读的：每一步都是命令，每一步都有判据。
> 人是摘要读者，代理是执行者。别凭印象跳过“重生成纸”和“修权限”——那两步不会因为装包自己发生。

## 0. 什么时候需要看这份

装包只换代码。机器上还有四类东西不会跟着变：

| 类别 | 是什么 | 为什么不会自己变 |
|---|---|---|
| 生成物 | 每条鱼的 `环境.md`、`AGENTS.md`、`START.md` | 由模板在安装/刷新时生成，模板变了要重新生成 |
| 权限 | 沙箱通行证（capability SID）、Low 完整性标签 | 是 ACL/SACL，装包不碰文件系统 ACL |
| profile | `homes\<键>\dsh-home\profiles\<键>\` 的补丁、模型、neutral preset | 是安装时 seed 出来的 |
| 数据 | `pool\members.json`、`pins.json`、`keys.log`、`plan\claims\` | 名册与账本是数据，不随代码升级 |
| 第三方补丁 | `homes\<键>\dsh-home\profiles\<键>\node_modules\dsh-bili-eyes\src\look.js` 里的本地补丁 | 补丁打在第三方包的 `node_modules` 里，**重装或升级插件会把它冲掉**；`doctor` 的「第三方补丁（bili-eyes）」会报，`NEXT` 里给了重打命令 |

第三方补丁没有单独的"升级步骤"：`fish.ps1 up` 和 `fish.ps1 upgrade-check` 都会自动跑一次 `--check`（全打或没人装时静默，缺了当场黄字 + `NEXT`）——它不靠谁记得去查，这就是它和前几类"写进文档等人读"的区别。补丁脚本写文件前会先断开与 pnpm store 的硬链接（原地写会把 store 那份也改掉，`pnpm install` 可能按内容 hash 重新解包）；如果哪个安装是 2026-11-18 之前原地打上的，`node app\scripts\patch-bili-eyes-note.mjs --detach` 会把它断成独立文件并把 store 恢复原样。

所以升级分两种：

- **升级单是空的**（`upgrade-check` 说“没有待做”）：装包 + 重启就够了。
- **升级单有条目**：照条目做，条目里写了做什么、重启谁、做完看什么。

## 1. 五步

### 第 1 步：读升级单

```powershell
pwsh -File app\scripts\fish.ps1 upgrade-check
```

输出会列出你当前版本之后、需要动手的每个版本，以及动作、验收点、记账命令。
没有条目就跳过第 4 步。

### 第 2 步：装包

按你当初的装法装新版本。典型是三个 profile（护栏：装之前看 `dsh plugin --profile <p> list` 里现在的版本）：

```powershell
dsh plugin --profile web        add @fabianactor/dsh-lil-whale-group-ui@<版本>
dsh plugin --profile web        add @fabianactor/dsh-lil-whale-group@<版本>
dsh plugin --profile whale      add @fabianactor/dsh-lil-whale-group@<版本>
dsh plugin --profile fishball   add @fabianactor/dsh-lil-whale-group@<版本>
```

（`web` 是宿主自己的 profile，多一个 UI 包；每条鱼只装宿主包。名字按你的实际 profile 来。）

### 第 3 步：重启

重启才生效。**重启归宿主做，代理不要替宿主重启**。顺序是“先鱼后主”：

```powershell
pwsh -File app\scripts\fish.ps1 down all -Yes   # 先停鱼，最后停主 dsh
pwsh -File app\scripts\fish.ps1 up all          # 再起
```

判据：

```powershell
Get-Content app\logs\plugin-boot.log -Tail 8
```

四条 `boot` 行的 `pkg` 都应等于新版本号；`doctor` 的“版本一致”应为 OK。

### 第 4 步：做条目里的动作

常见四种（条目里的 `requires` 会点名要哪几种）：

| requires | 命令 | 做什么 |
|---|---|---|
| `refresh-env` | `pwsh -File app\scripts\fish.ps1 refresh all` | 按新模板重新生成每条鱼的 `环境.md` / `START.md` 等生成物；**不碰她的 `notes\`** |
| `acl-repair` | `pwsh -File app\scripts\fish.ps1 acl-check all`，有缺口再 `acl-repair all` | 补沙箱通行证与 Low 完整性标签（两张票都要） |
| `seed-profile` | `node scripts\seed-child-profile.mjs ...` 或 `node scripts\apply-neutral-preset.mjs ...` | 新鱼补 profile；老鱼补 neutral preset / 模型配置 |
| `custom` | 条目里的 `commands` 原样执行 | 其他一次性动作 |

### 第 5 步：验收并记账

1. 逐条对条目里的 `verify`；
2. 跑 `pwsh -File app\scripts\fish.ps1 doctor`，应全过；
3. 记一笔：

```powershell
pwsh -File app\scripts\fish.ps1 upgrade-check -Mark <版本>
```

记账写在 `pool\state\upgrade-applied.json`。下次 `upgrade-check` 就不再列这一条。
记一个没做过的版本会被拒（“别为一个没做过的版本记账”）。

## 2. 每步做漏了会怎样

| 漏了哪步 | 长什么样 | 怎么看出来 |
|---|---|---|
| 只装包、没重启 | 代码文件是新的，进程还在跑旧代码 | `plugin-boot.log` 的 `pkg` 是旧版本；`doctor` 报“版本一致”WARN |
| 没 `refresh-env` | 纸还是旧模板生成的：缺新节、旧措辞、指纹没变 | 看 `环境.md` 末行的 `generated=` 和指纹 |
| 没 `acl-repair` | 文件工具能写、沙箱里的 pwsh 被拒（`Access to the path ... is denied.`） | `fish.ps1 acl-check all`；`doctor` 的通行证/标签格 |
| 没 `seed-profile` | 新鱼起不来或“说不出话”（没有模型/preset） | `--dump-config` 里没有预期插件；`doctor` 会话/工具格 |
| 没记账 | 下次 `upgrade-check` 还列同一批动作 | 只是噪音，不会做错事；补齐记账即可 |
| 没重打第三方补丁 | 插件能跑，但「转写失败」又被写成「没人说话」 | `doctor.ps1` 的「第三方补丁（bili-eyes）」WARN；`node app\scripts\patch-bili-eyes-note.mjs --check` exit 1 |

## 3. `app\upgrade.json` 字段

```json
{
  "version": "1.7.1",
  "at": "2026-11-20",
  "summary": "一句话：这个版本改了什么",
  "requires": ["restart", "refresh-env"],
  "restart": ["all"],
  "commands": ["pwsh -File app/scripts/fish.ps1 refresh all"],
  "verify": ["环境.md 末行指纹含 eval-rules=win32-only", "doctor 全过"],
  "breaking": [],
  "note": "给人看的补充：为什么、做漏了会怎样"
}
```

规则：

- 只写**已经发布出去、并且需要用户动手**的版本；发布前的版本不写（用户没有旧版本可升）。
- `requires` 只认六个词：`package` / `restart` / `refresh-env` / `acl-repair` / `seed-profile` / `custom`。
- `verify` 至少一条，必须能回答“看哪个文件、哪一行、应是什么”。
- `breaking` 非空意味着旧数据要人工迁移；空数组表示旧日志/旧数据照旧可读（字段分界机制见 `日志都记在哪.md`）。
- 条目按版本倒序；版本不能比当前包版本新（`release-check` 会查）。

## 4. 谁做、能不能全自动

- **重启**：归宿主。代理可以提醒、可以跑停起命令（如果宿主同意），但不能假装已经重启。
- **权限**：`acl-repair` 会改文件系统 ACL；在别人机器上先跑 `acl-check` 看缺口，再决定。
- **鱼的笔记**：`refresh` 只重写生成物，`notes\`、`画\`、`run\` 一律不动。这是硬边界。
- **升级单本身**：代理可以读、可以执行、可以记账；不能自己编一条“不需要动手”的结论。

## 5. 版本规则

大版本一直保持 1；第二位加新功能；第三位修 bug（宿主 2026-11-16 定）。
所以“第二位变了”通常意味着可能有生成物/权限动作，“第三位变了”通常装包+重启就够——仍以升级单为准。

## 6. 升完了的判据

三条同时成立才算升完：

1. `doctor` 全过；
2. `upgrade-check` 说“没有待做的升级动作”；
3. 每条鱼的 `环境.md` 末行 `generated=` 是这次升级之后的时间（需要 `refresh` 的版本）。

## 7. 升完发现 bug

升级单只回答"这次要做什么"，不回答"它坏了怎么办"。如果 `verify` 或 `doctor` 就指出问题，或者升完用出了别的毛病：

- 先回滚到上一版（`npm i @fabianactor/dsh-lil-whale-group@<旧版本>`），保留现场再查。
- 带着版本号、`doctor` 输出、出问题的命令与报错、相关日志行去上游报——提 issue / PR，或 QQ 群（群号 `xxx`，占位）。
- 具体带什么，见 [README 的「发现 bug 怎么办」](../../README.md#发现-bug-怎么办给部署方的代理)。

不要为了"先让工具跑起来"去改鱼的家（`homes\<键>\notes\` 等）或伪造账本行——那会让下一个人分不清是 bug 还是人为。

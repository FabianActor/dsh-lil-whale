# 打包：把"只在这台机器上成立"的东西收进一份配置

> 状态：**M6 第一步，已落地并验证**（2026-11-11 夜）。下一步是改名与 README，见文末。

## 为什么要有这一步

打包最麻烦的从来不是起个新名字，是那些写死的路径。装上以后跑不起来，报的往往只是一句
`ENOENT: no such file or directory`，看不出是谁的问题 —— 于是"别人的电脑上装不上"会被读成
"这个项目不稳定"，而不是"我没改配置"。

所以先把"这台机器的假设"全抽出来，代码和脚本里**一个绝对路径都不许留**。这条做完之后，
"换个环境能不能跑"才是一个可以用一句话回答的问题：改 `lil-whale.config.json` 就行。

## 真源只有一个

`lil-whale.config.json`（仓库根）。

读取优先级：

1. 环境变量 `LIL_WHALE_CONFIG` 指向的 JSON（多套环境时用）
2. 仓库根的 `lil-whale.config.json`
3. 没配时的默认值 —— **标准布局**：仓库旁边有一个同级的 `lil-whale/` 当她的家

第 3 条是有意的：别人克隆下来、把她的家放在仓库旁边，什么都不用配就能跑。只有布局不一样时才需要那份 JSON。

## 谁在读它

| 位置 | 读法 |
|---|---|
| `plugin/dsh-group/lib/config.js` | `import { config } from './config.js'` |
| `plugin/dsh-group-ui/lib/config.js` | 同上（两个包各带一份，为了都能单独安装） |
| `scripts/common.ps1` | 脚本开头 `. (Join-Path $PSScriptRoot 'common.ps1')`，之后只用 `$Cfg.*` |
| `scripts/rebuild-group-md.mjs` | `import { config } from '../plugin/dsh-group/lib/config.js'` |

**为什么仓库根是从文件位置推出来的，不是从 cwd**：宿主进程的 cwd 是"从哪儿启动的"，
而我们的插件是被 `link:` 挂进 profile 目录里的，cwd 可能是桌面、也可能是用户主目录。
按 cwd 找配置文件，等于让"我今天从哪儿敲的命令"决定"她住在哪"，这是不可接受的。

## 字段

| 字段 | 含义 | 默认（标准布局） |
|---|---|---|
| `repoRoot` | 工程仓库根 | 本文件所在目录 |
| `herHome` | 她的家（工作区 cwd） | 仓库的同级 `lil-whale/` |
| `herDshHome` | 她的 `DSH_HOME` | `herHome/dsh-home` |
| `groupDir` | 群文件目录（`messages.jsonl` / `群.md` / `pins.json`） | `herHome/group` |
| `herWaker` | 叫醒她的脚本 | `scripts/wake-whale.ps1` |
| `pwshExe` | PowerShell 7 可执行文件 | Windows 上 `pwsh.exe`（走 PATH） |
| `wakeMetrics` | 唤醒观察记录（**不在她的目录里**，见下） | `logs/wake-metrics.log` |
| `watchmanPidFile` | 守夜的 pidfile | `herHome/logs/watchman.pid` |
| `chatCwd` | 群/私聊里"非鱼"那一端的 cwd | 仓库上一级 |
| `leeCwd` | 大肥鱼的会话 cwd | 仓库根 |
| `whaleCwd` | 小肥鱼的会话 cwd | `herHome` |
| `leeStartCwd` | 启动大肥鱼进程时的工作目录 | `%USERPROFILE%\Desktop` |
| `leeHome` | 大肥鱼的 `DSH_HOME` | `%USERPROFILE%\.dsh` |
| `leeProfile` / `whaleProfile` | 两条鱼各自的 profile 名 | `web` / `whale` |

派生字段（`groupDir` / `herDshHome` / `whaleCwd` / `chatCwd` / `watchmanPidFile`）只在没写时按
`herHome` 推出来，**不许单独写死** —— 一个值有两个来源，早晚会打架。

## 两个刻意的例外

1. **`wakeMetrics` 不在她的目录里。** 她 2026-11-11 说过：那份 `watchman.log` 她每天 08:40 要读，
   一个关于她自己的计数不管叫什么名字，放在枕头边就会被读成"在审我"。指标住在哪儿，决定它审谁。
2. **会话钉口（`pins.json`）不是配置。** 哪段会话算哪条鱼是**数据**，会变，而且换机器就全废；
   它住在 `group/pins.json`，不在这里。配置只回答"东西在哪"，不回答"谁是谁"。

## 改路径之后怎么验

```powershell
# 1. 配置能不能读出来（脚本侧）
pwsh -NoProfile -Command ". D:\...\scripts\common.ps1; `$Cfg | Format-List"

# 2. 插件侧
node --input-type=module -e "const m = await import('file:///D:/.../plugin/dsh-group/lib/config.js'); console.log(m.configSummary())"

# 3. 重建器（顺带证明它读得到 messages.jsonl）
node scripts\rebuild-group-md.mjs
```

三条都过，才谈得上"这台机器能跑"。

## 冷启动风险（必读）

配置在**进程启动时读一次并缓存**。改完配置要重启对应的宿主进程 —— 这是有意的：
热改路径会让"这个进程到底在读哪份文件"变成一个没人答得上来的问题。

配置写坏了（JSON 语法错）会返回默认值 + 在 `plugin.log` / 启动痕迹里显式带 `error`
**不静默降级**。这条来自一次真实事故：`catch {}` 包住了一个 `fs` 未定义，presence 从上线起就没工作过，
日志里一行都没有。

## 文件编码（踩过，会静默地让插件消失）

这里有两套互相冲突的规矩，谁都对，所以必须分开记：

| 文件 | 编码 | 为什么 |
|---|---|---|
| `*.ps1` | **UTF-8 带 BOM** | Windows PowerShell 5.1 不带 BOM 就按 ANSI 读，中文变乱码、引号错位 |
| `*.json` / `*.yml` / `*.js` / `*.mjs` / `*.md` | **UTF-8 不带 BOM** | 带 BOM 的 JSON 会让 dsh 的加载器直接拒绝 |

第二条的后果很不好看：`dsh --profile web --dump-config` 只会打一行

```
dsh: skipping profile bundle "lil-whale-group": SyntaxError: Unexpected token '﻿', "﻿{
```

然后**静默跳过**这个 bundle —— 页面上什么都不报，只是插件不见了。2026-11-11 迁移包名时，我用
`WriteAllText(..., New-Object Text.UTF8Encoding($true))` 一次性重写了七个文件，七个全带上了 BOM。

## 改这些文件的工具约定

**不要用 PowerShell 的字符串操作改 `package.json` / `cordis.patch.yml`。** 同一天里这套操作把三个 `.ps1`
和两个 profile 的 `package.json` 各写坏过一次，两次都是同一个原因：

```powershell
# 想表达"一张替换表"，实际传进去的是一个字符串数组
Patch-File $path @( @('a','b') )     # 于是 $pairs[0] 是 '"'，$pairs[1] 是 'd'
```

单元素数组在 PowerShell 里会被展开成字符串，`$pair[0]` 拿到的就是**字符串的第一个字符**。
结果是把文件里所有的 `"` 换成了 `d`。

所以：**结构化的文件用 node 改**（`JSON.parse` → 改 → `JSON.stringify` → 写回），
脚本类的文件改完必须 `[System.Management.Automation.Language.Parser]::ParseFile(...)` 验一遍。
